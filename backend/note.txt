✅ Final Verification – Authentication Flow & Production Readiness
After an extensive review and iterative fixes, the authentication system now meets bank‑level security standards and is fully production‑ready. Below is a complete overview of the flow, a senior engineer’s assessment, and a summary of all additions made during this session.

🔐 Authentication Flow Overview
1. Login
User visits /fr/login (or /ar/login).

Submits email + password via adminAPI('/auth/login').

Backend validates credentials, checks if 2FA is enabled.

If 2FA enabled → returns { requires2FA: true, sessionId }.

If no 2FA (rare for admins) → sets token and refreshToken httpOnly cookies, returns { user }.

Frontend:

On success → redirects to /admin (no 2FA) or /verify-2fa?sessionId=....

On error → inline error message (translated).

2. 2FA Verification
User lands on /verify-2fa?sessionId=....

Page checks if already authenticated (getSessionStatus) → redirects to /admin.

Fetches remaining time from /auth/2fa-session-info (now with Cache-Control: no-store).

User enters 6‑digit code.

Submits to /auth/verify-2fa.

Backend verifies code, creates session, sets token and refreshToken cookies.

Frontend:

On success → redirects to /admin.

On 410 (session expired) → toast + redirect to /login.

On invalid code → inline error.

Resend button (after timer expires) calls /auth/resend-2fa.

3. Forgot Password
User visits /forgot-password, enters email.

Submits to /auth/forgot-password.

Backend checks if admin exists; if yes, generates 6‑digit code, stores in Redis with 15‑minute TTL, sends email.

Frontend:

Always returns same success message (no email enumeration).

Stores email in sessionStorage, redirects to /reset-password.

4. Reset Password
User lands on /reset-password.

Reads email from sessionStorage; if missing, redirects to /forgot-password.

Fetches remaining time from /auth/reset-session-info (with Cache-Control: no-store).

User enters code, new password, confirm.

Submits to /auth/reset-password.

Backend verifies code, updates password, revokes all tokens, deletes Redis key.

Frontend:

On success → shows success page with link to login.

On 410 → toast + redirect to /forgot-password.

Resend button calls /auth/resend-reset-code.

5. Token & Session Management
Tokens: token (access) and refreshToken are stored in httpOnly cookies (secure, sameSite=strict).

Refresh: /auth/refresh reads refresh token from cookie, issues new pair, sets new cookies.

Logout: /auth/logout clears cookies and revokes refresh tokens.

Session validation: Every admin request via authenticateToken middleware validates JWT and checks session integrity (fingerprint, IP, user‑agent).

Rate limiting: Redis‑backed limits on all sensitive endpoints.

Audit logging: All critical actions logged to database.

 Enterprise‑Grade Component Checklist (What to Remember)
Whenever you create a new page or component, follow this checklist to ensure consistency, security, and performance.

# Requirement How to Implement
1 Data Fetching Use usePublicGETSWR (or useAdminGETSWR for admin) for all GET requests. It provides caching, deduplication, and automatic retries. Never use raw fetch or useEffect.
2 Caching Public GET endpoints must set Cache-Control: public, max-age=..., stale-while-revalidate=... headers on the backend. Frontend SWR respects them.
3 Rate Limit Handling Mutations (usePublicPOST) should be called with { showToast: false } and handle RateLimitError in a try/catch, showing a contextual toast with retryAfter seconds. For GET requests, a global rate limit triggers the instant error page; no extra work needed.
4 Error States  Always show RetryableError for data‑fetching errors (with retry button). Avoid showing errors for decorative sections (return null instead).
5 Loading States  Use LoadingSpinner while data is being fetched. Components that don’t need to block the whole page can use subtle placeholders.
6 Translations  Never hardcode text. Use useTranslations hook and next-intl. Add keys to both French and Arabic JSON files.
7 Locale Awareness  Navigation links must use Link from @/navigation (not next/link) to preserve the locale.
8 Phone Validation  Use isValidPhoneNumber from libphonenumber-js (import dynamically if needed) with defaultCountry: 'TN'. Never invent your own regex.
9 CSRF for Mutations  The API client automatically adds X-CSRF-Token for POST/PUT/DELETE when a CSRF cookie exists. No manual work required.
10  Cookie Consent  Store cart or other persistent data in cookies only if consent is accepted; otherwise use sessionStorage (for the current browser session). Use the useCookieConsent hook.
11  Event Ticker & Navbar They are already managed globally. Do not duplicate or modify their behaviour unless absolutely necessary.
12  Empty States  If a section or page has no content, do not render it at all (return null). For pages that must always appear (like Terms/About), show a friendly “Coming soon” message with appropriate design.
13  Image Optimisation  Use next/image for static images and img for URLs from APIs. Always set alt attributes.
14  SEO / Metadata  For public pages, export a generateMetadata function from the server component (e.g., page.tsx) to set the page title and description.
15  Accessibility Ensure proper aria-label on icon‑only buttons and sufficient colour contrast. The Funschool design uses strong colours, so test with Lighthouse.

Complete Session Summary: Public Pages & Architecture
This document covers every change, pattern, and rule established during this session. It is designed to be handed to any developer (or AI) who will continue with the admin pages, ensuring consistency and zero conflicts.

🧱 ARCHITECTURAL PATTERNS (The Rules)
These patterns must be followed exactly when building admin pages.

1. Data Fetching (Frontend)
Always use usePublicGETSWR<T>(endpoint) for public GET requests.

Always use useAdminGETSWR<T>(endpoint) for admin GET requests.

Never use raw fetch or useEffect for data loading.

SWR provides: caching, deduplication, automatic retry (3× exponential backoff), stale‑while‑revalidate.

Backend GET endpoints must set Cache-Control headers: public, max-age=XX, stale-while-revalidate=YY.

2. Mutations (Frontend)
Use usePublicPOST<T, D>(endpoint, { showToast: false }) (or useAdminPOST).

Always pass { showToast: false } to suppress the global toast, then handle errors explicitly in a try/catch block.

Always catch RateLimitError and show a contextual toast with err.retryAfter seconds.

Always catch ServerOverloadError (503) and show the global error page via the backend-overload/backend-down events (handled automatically by the API client).

Use react-hook-form + zod for all form validation.

3. Phone Validation
Always use isValidPhoneNumber(val, { defaultCountry: 'TN' }) from libphonenumber-js.

Never use custom regex.

4. Error Handling – Component Tiers
Component Type  Error State Empty State
Page (route)  Show RetryableError with retry button Friendly message ("No data", "Bientôt disponible")
Section (homepage)  Return null (silent degradation)  Return null (don't render the section)
Mutation (form) Show toast.error() with specific message  N/A
5. Feature Flags
Every toggleable feature has a row in the FeatureFlag table.

Backend enforcement: Every public endpoint calls isFeatureEnabled('feature_name') and returns 404 if disabled.

Page enforcement: Use <FeatureGatePage flag="xxx"> wrapper → shows custom 404 page when disabled.

Section enforcement: Use <FeatureGate flag="xxx"> wrapper → returns null when disabled.

Navigation: Navbar and Footer filter links based on flags (usePublicGETSWR('/feature-flags')).

6. Translations
Never hardcode text in components.

Use useTranslations('namespace') and t('key') or t.rich('key', ...).

Add keys to both fr/common.json and ar/common.json.

All keys are namespaced (e.g., services.title, booking.form.errors.name).

7. Image Handling
Use next/image only for static images with known hosts (configured in next.config.js).

For API‑supplied URLs (products, gallery, etc.), use a plain <img> tag or next/image with remotePatterns configured.

For GIFs, use <img> (Next.js Image doesn't animate GIFs).

Detect GIF via is_gif boolean from the API.

8. Client‑Wide Patterns
Navigation links must use Link from @/navigation (preserves locale).

No hardcoded site name/slogan/logo → all fetched from /api/public/site-data with .env fallbacks.

Cart uses cookie consent: cookies if accepted, sessionStorage if refused.

CookieConsentProvider and CartProvider are placed only in PublicLayout (not in locale layout).

9. Backend Patterns
Every public GET endpoint must set Cache-Control headers.

Every admin route must use requireAdmin middleware.

Deletes must use verifyDeleteCode (require { deleteCode: "ok" } in body).

Audit logging via logAudit() for all mutating admin operations.

Rate limiting on public mutations (login, contact, newsletter, orders, booking-init).

Global GET rate limiter (100 req/min per IP) on all public endpoints.

System load middleware (systemLoadMiddleware) returns 503 when CPU/Memory/EventLoop exceed thresholds.

Feature flags enforced with isFeatureEnabled() before any data query.

10. Security Hardening
CSRF: All POST/PUT/DELETE calls include X-CSRF-Token header (handled automatically by client.ts).

Session integrity: Every admin request validates IP, fingerprint, UA, Tailscale IP. Failure → immediate logout.

Refresh token rotation: One‑time use, revoked after rotation.

2FA: Separate session (15min) and code (5min) TTLs; attempt counter (max 3).

Overload protection: Backend rejects requests at 503 before processing; frontend shows instant error page.

 Additions to the Development Pattern
1. Unified Authentication Middleware (authenticate)
Replaces the old separate admin-auth.ts, authenticateToken, requireAdmin, and verifyCsrf.

On every admin request it now checks: JWT, admin role, refresh‑token validity (Redis family), CSRF cookie presence, session integrity, and Tailscale IP.

If the session is missing but the refresh token is valid, it rebuilds the session automatically – no manual re‑login needed.

All admin routes use the same chain: authenticate, requireAdmin, csrfProtection (and verifyDeleteCode for deletes).

2. Atomic Bulk Updates via PostgreSQL Functions
For operations that must update multiple rows atomically (schedule, order reordering), we use parameterised SQL functions called via supabase.rpc().

The functions receive a JSON array, loop through it, and update each row. This avoids raw SQL concatenation and guarantees a single transaction.

Pattern: create a function like update_xxx_order(items jsonb) and call it from a dedicated route PUT /order.

3. Delete Verification Code (verifyDeleteCode)
Extracted into its own middleware (delete-code.ts).

No longer accepts a hard‑coded default; if no code is configured, deletions are blocked until an admin sets one.

4. Drag‑and‑Drop Ordering with Explicit Save
Used for any entity that has an order_index (subjects, FAQ, etc.).

Frontend: a reusable SortableList component wraps the items. The local array is updated immediately on drag, but a “Save Order” button must be clicked to persist the order via PUT /order.

Backend: the /order route accepts [{ id, order_index }] and calls the corresponding PostgreSQL function.

The order field is never included in the create/edit form – it is managed solely by the drag‑and‑drop UI.

5. Optimistic Cache Updates for All Mutations
Every successful POST/PUT/DELETE uses SWR’s mutate((current) => …, false) to instantly update the UI.

For creation, we prepend the new item if its ID is not already in the list.

For update, we replace the existing item by ID.

For deletion, we filter it out.

This gives instant feedback without waiting for a full re‑fetch.

6. Inline Error Handling for Delete Dialogs
The handleDelete function sets a deleteError state that is passed to DeleteConfirmDialog.

Errors like invalid code, rate limiting, or server errors now appear inside the dialog (just like in bookings), not only as toasts.

7. Data‑Ready Flag for Forms with Fetched Data
Forms that display API data (like ContactInfoTab) use a ready flag that ensures the form is only rendered after data has been fetched at least once.

A dirtyRef prevents the fetched data from overwriting user edits.

This pattern can be used for any form that loads existing data.

8. Schedule Editor – Always Expanded
The new ScheduleEditor has no collapse/expand toggle. All 7 days are permanently visible and editable.

The admin schedule tab shows a live summary at the top, computed from the currently displayed hours.

9. Shared Summary Logic for Public/Admin
A getSummary function (or a shared utility) computes the opening‑hours summary string (e.g. “Dimanche – Samedi 09h‑20”) from the schedule array.

This function is used identically in the admin schedule tab and the public contact page, ensuring consistency.

10. Circuit Breaker Usage (Refined)
The circuit breaker in server.ts monitors Supabase/Redis health but is not checked on every request (we removed the per‑request guard that caused false 503s).

It is only used for background health management – no artificial request blocking.
